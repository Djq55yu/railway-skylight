> 目标：三个接口 + 三张表，让确认台上的选择**落得下来、查得回去、导得出去**。
> 前置：PR #5 合并后，`backend/.../agent/` 里已有 `/check` `/explain` `/ping` 三个端点可参考。

## 1. 为什么做

现在智能体这一侧已经闭环：

```
AgentArts 三个运行时（核查 / 编排 / 仲裁）  → 云端已跑通
taskMode=PRE_REVIEW                       → 返回 A/B 方案 + 仲裁建议 + 5 条留痕
```

但产品这一侧漏了两段：

1. **前端不能直接调云端**（IAM AK/SK 签名在服务端，浏览器里放不了密钥）→ 需要一个代理接口
2. **「人选了哪套」没有任何地方记** → 答辩被问「决策谁做的、凭什么」时拿不出证据

这三张表 + 三个接口就是补这两段。

## 3. 接口契约

### 3.1 `POST /api/agent/negotiate`（P0，前端阻塞在这一条）

**做什么**：拼 payload → 调云端 `taskMode=PRE_REVIEW` → 原样返回结构化结果。

```json
// 请求（二选一）
{ "windowId": 9 }
{ "windowStart": "07:30", "windowEnd": "09:20" }

// 响应
{
  "sessionId": "S-01b938ba3de8",
  "taskMode": "PRE_REVIEW",
  "plans": [
    { "planId": "A", "name": "检查工区顺延",
      "movedTasks": [24, 25, 26, 28, 30, 31],
      "cost": { "affectedTeam": "萍乡检查工区", "movedCount": 6,
                "workloadRisk": "6 条检查作业需另排天窗，可能延后 1 天",
                "safetyGain": "重叠消除，天窗内无跨工区交叉作业",
                "quantified": { "冲突": "归零", "延期作业": 6, "延期天数": "1" } } },
    { "planId": "B", "name": "保留全部 · 分区分界", "movedTasks": [], "cost": { … } }
  ],
  "checks": [ { "planId": "A", "conflictCount": 0, "severe": 0, "normal": 0 },
              { "planId": "B", "conflictCount": 10, "severe": 6, "normal": 4 } ],
  "verdict": { "recommended": "A", "recommendedName": "检查工区顺延",
               "reason": "方案 A 严重冲突 0 条，方案 B 为 6 条；安全优先取 A。",
               "fallback": "若方案 A 的代价不可接受 → 改取方案 B，并按 2.2.10 第 1 款……",
               "requiresHumanChoice": true },
  "conflicts": [ { "type": "作业单元冲突", "serialNos": [18, 49],
                   "ruleRef": "2.2.10 第 1 款", "severity": "严重",
                   "suggestion": "按 2.2.10 第 1 款由车务段指定主体单位并划分分界点" } ],
  "trace": { "sessionId": "S-…", "events": [ … 5 条 … ] },
  "source": "cloud"      // cloud / local（降级时）
}
```

**实现建议**：和 `AgentExplainService` 同一套路 —— 拼 JSON → `explain_bridge.py`（或新建一个
`negotiate_bridge.py`）→ 解析 stdout。区别只是 payload 里多了 `"taskMode":"PRE_REVIEW"`。

**四条硬要求**：

| 要求 | 说明 |
|---|---|
| 超时 60 s | 运行时冷启动实测 10–30 s，超时别设太短 |
| 幂等 | 同一 `(windowId, 排序后的 taskIds)` 5 分钟内返回同一结果（简单 LRU 缓存即可），避免重复烧模型 |
| 降级 | 云端不可用 → `source: "local"` + 本地规则结果 + `note` 说明。**HTTP 仍是 200**，前端只认字段不认状态码 |
| 日志 | 打印 `sessionId` / 耗时 / `source`；**不要打印 payload 原文**（含工区负责人姓名与电话） |

### 3.2 `POST /api/agent/decide`（P0，决策落库）

```json
// 请求
{ "sessionId": "S-01b938ba3de8", "windowId": 9,
  "choice": "A", "reason": "安全优先，接受检查工区延期 1 天",
  "operator": "调度员" }

// 响应
{ "status": "ok", "decisionId": 12, "acceptedAt": "2026-11-15T02:20:11+08:00" }
```

规则：
- `choice` 只接受该 `sessionId` 下 `plans[].planId` 里的值，其余返回 400
- 同一 `sessionId` 重复提交 → 覆盖（`human_accepted` 记 1，保留最后一次）
- **智能体自己给的建议也要存**（`by_role='ARBITER'`, `human_accepted` 由 decide 时回填）

### 3.3 `PATCH /api/conflicts/{id}`（P0，状态落库）

```json
{ "status": "HANDLED" }     // PENDING / HANDLED / IGNORED
```

- `{id}` 用前端的稳定键：`type + "|" + involved`（URL 编码），或后端生成 hash
- 返回 `{ "status": "ok", "updatedAt": "…" }`
- 不存在则 upsert（前端可能先标状态后建记录）

### 3.4 留痕查询 / 导出（P1）

```
GET /api/agent/session/{sessionId}          → { session, messages[], decision }
GET /api/agent/session/{sessionId}/export   → 一页 Markdown（给评委看）
```

## 4. 表设计（建议，字段名可改）

```sql
CREATE TABLE agent_session (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  session_id   VARCHAR(64)  NOT NULL UNIQUE,
  window_id    BIGINT,
  task_mode    VARCHAR(32)  NOT NULL DEFAULT 'PRE_REVIEW',
  agent_name   VARCHAR(64),
  started_at   DATETIME     NOT NULL,
  finished_at  DATETIME,
  status       VARCHAR(16)  NOT NULL DEFAULT 'OK',
  KEY idx_window (window_id)
);

CREATE TABLE agent_message (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  session_id  VARCHAR(64) NOT NULL,
  seq         INT         NOT NULL,
  speaker     VARCHAR(32) NOT NULL,     -- ORCHESTRATOR / CHECKER / ARBITER
  target      VARCHAR(32),
  kind        VARCHAR(32) NOT NULL,     -- plans / check_result / checked
  payload     JSON,
  created_at  DATETIME    NOT NULL,
  UNIQUE KEY uk_session_seq (session_id, seq)
);

CREATE TABLE agent_decision (
  id              BIGINT AUTO_INCREMENT PRIMARY KEY,
  session_id      VARCHAR(64) NOT NULL,
  by_role         VARCHAR(32) NOT NULL,   -- ARBITER（机器建议）/ HUMAN（人选的）
  choice          VARCHAR(16),
  reason          TEXT,
  human_accepted  TINYINT     NOT NULL DEFAULT 0,
  operator        VARCHAR(64),
  decided_at      DATETIME    NOT NULL,
  KEY idx_session (session_id)
);

CREATE TABLE conflict_status (
  conflict_key  VARCHAR(128) PRIMARY KEY,   -- '作业单元冲突|18,49'
  window_id     BIGINT,
  status        VARCHAR(16)  NOT NULL,      -- PENDING / HANDLED / IGNORED
  operator      VARCHAR(64),
  updated_at    DATETIME     NOT NULL
);
```

**三表的分工**（写进方案的）：

| 表 | 一次协商产生几行 |
|---|---|
| `agent_session` | 1（一次编排） |
| `agent_message` | 4（编排→核查、核查→编排 ×2、核查→仲裁） |
| `agent_decision` | 1（仲裁建议）+ 1（人选，若已选） |

## 6. 不做的事

- 不做多用户 / 鉴权（演示场景单人）
- 不做定时任务、不做异步队列（同步调用足够，60 s 超时兜底）
- 不改现有 `ConflictController` 的返回结构（三页前端还在用）
- 不在后端复算冲突（判定只在 `AgentCheckService` / 运行时里做一份）
