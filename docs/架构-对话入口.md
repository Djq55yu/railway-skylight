## 一、一句话

**对话入口是一个「两轮工具调用」的状态机：模型负责听懂要什么数据，后端负责去取；取回来的数据交给同一个运行时，最后落到已有的判定与协商链路上。**

---

## 二、分层

```
┌─────────────────────────────────────────────────────────────┐
│ 前端  #chat       只说人话：输入框 + 气泡 + 结果卡            │
└──────────────────────────┬──────────────────────────────────┘
                           │ POST /api/agent/chat { text }
┌──────────────────────────▼──────────────────────────────────┐
│ 后端（宿主，连 MySQL）                                        │
│  ① 调 runtime：mode=CHAT, round=1                             │
│  ② status=tool_call → 执行工具（查库）→ 再调一次               │
│  ③ 终态 → 渲染给前端；出错 → 降级成「手动选天窗」              │
└──────────────────────────┬──────────────────────────────────┘
                           │ /invocations（IAM 签名）
┌──────────────────────────▼──────────────────────────────────┐
│ AgentArts 运行时（无状态、不连库、不挂卷）                     │
│  mode=CHAT          听懂 → 要数据 → 定 windowId               │
│  mode=NEGOTIATE     判定（纯函数）+ 条文检索 + 措辞            │
│  镜像内唯一数据：clauses.json（条文库）                        │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTPS
                     MaaS 模型（只选择、只措辞）
```

## 三、职责边界

| 层 | 负责 | **不负责** |
|---|---|---|
| 前端 | 展示；把用户的话原样送出 | 不理解、不计算 |
| 后端 | 取数、执行工具、路由、持久化、降级 | 不判定、不解释 |
| 运行时 | 理解意图、判定、条文检索、措辞 | **不连库、不落盘、不调别的运行时** |
| 模型 | 抽参数、在候选里选、把结论说顺 | **不判定、不造条号** |

## 四、一次对话的完整时序

```
用户：核查 9 月 23 号那个天窗
  │
  ├─ ① 后端 → runtime   {mode:CHAT, text, round:1}
  │
  ├─ ② runtime → 后端   {status:"tool_call",
  │                      tool_calls:[{name:"list_windows", args:{date:"2026-09-23"}}]}
  │
  ├─ ③ 后端查库 → 2 个候选窗口
  │
  ├─ ④ 后端 → runtime   {mode:CHAT, text, round:2, tool_results:[…]}
  │
  ├─ ⑤ runtime → 后端   {status:"ok",
  │                      command:{windowId:9, taskMode:"PRE_REVIEW"},
  │                      echo:"2026-09-23 07:30—09:20，12 条作业"}
  │
  ├─ ⑥ 后端执行 command → 调 runtime（NEGOTIATE / PRE_REVIEW）
  │                     返回 plans / checks / verdict / conflicts / trace
  │
  └─ ⑦ 后端 → 前端      {echo, reply, plans, verdict, conflicts}
```

**用户只看到 ⑦。中间两轮工具调用不可见。**

## 五、三份契约

### 5.1 对话请求

```json
{ "mode": "CHAT", "text": "核查 9 月 23 号那个天窗", "round": 1 }

{ "mode": "CHAT", "text": "…", "round": 2,
  "tool_results": [
    { "name": "list_windows",
      "result": [ {"windowId": 9,  "date": "2026-09-23", "start": "07:30",
                   "end": "09:20", "taskCount": 12},
                  {"windowId": 10, "date": "2026-09-23", "start": "10:40",
                   "end": "13:10", "taskCount": 5} ] } ] }
```

### 5.2 对话响应（`status` 决定后端分支）

| status | 必带字段 | 含义 |
|---|---|---|
| `tool_call` | `tool_calls[]` | 还要数据（**仅第 1 轮允许**） |
| `ok` | `command`, `echo`, `reply` | 终态，可直接回答 |
| `need_choice` | `candidates[]` | 终态，有歧义 |
| `not_found` | `reply` | 终态，没找到 |
| `error` | `reply` | 终态，走降级 |

```json
// tool_call
{ "status": "tool_call",
  "tool_calls": [ {"name": "list_windows", "args": {"date": "2026-09-23"}} ] }

// ok
{ "status": "ok",
  "command": { "windowId": 9, "taskMode": "PRE_REVIEW" },
  "echo": "2026-09-23 07:30—09:20，12 条作业",
  "reply": "本次天窗检出 10 条冲突，6 条严重；建议方案 A（检查工区顺延），冲突可归零…",
  "confidence": 0.93 }

// need_choice
{ "status": "need_choice",
  "candidates": [ {"windowId": 9,  "label": "09-23 07:30—09:20 · 12 条"},
                  {"windowId": 10, "label": "09-23 10:40—13:10 · 5 条"} ] }
```

### 5.3 工具清单（白名单，只给三个）

| 工具 | 参数 | 返回 |
|---|---|---|
| `list_windows` | `date` / `start` / `end` | 候选天窗列表 |
| `get_window_tasks` | `windowId` | 该窗作业（可选） |
| `get_clause` | `ruleRef` | 条文原文（可选） |

## 六、状态机

```
round=1 ──┬─ ok / need_choice / not_found / error ──► 终态
          └─ tool_call ──► 执行工具 ──► round=2
                                          ├─ 终态 ──► 返回前端
                                          └─ tool_call ──► 判 error（超轮次）
```

**最多两轮。** 第二轮不允许再申请工具。

---

## 七、六条护栏

| # | 护栏 | 防什么 |
|---|---|---|
| 1 | `status` 必须属于枚举，未知即 error | 模型乱写控制流 |
| 2 | 最多 2 轮 | 无限调用 |
| 3 | 工具名白名单 | 模型调不该调的 |
| 4 | 参数校验（日期格式、windowId 在候选内） | 编造参数 |
| 5 | 超时 / 异常 → 降级成「手动选天窗」 | 云端抖动拖垮页面 |
| 6 | 日志只打 sessionId / 耗时 / status，不打 payload | 数据泄露 |

### 后端伪代码

```java
public ChatResponse chat(String text) {
    JsonNode r1 = invokeRuntime(Map.of("mode","CHAT","text",text,"round",1));

    String s1 = norm(r1.path("status").asText(""));       // trim + lower + 下划线归一
    if (!STATUSES.contains(s1)) return fallback("返回格式异常");
    if (!"tool_call".equals(s1)) return toResponse(r1);

    List<Map<String,Object>> results = new ArrayList<>();
    for (JsonNode c : r1.path("tool_calls")) {
        String name = c.path("name").asText();
        if (!TOOLS.containsKey(name)) return fallback("未授权工具：" + name);
        results.add(TOOLS.get(name).exec(c.path("args")));
    }

    JsonNode r2 = invokeRuntime(Map.of("mode","CHAT","text",text,
                                       "round",2,"tool_results",results));
    String s2 = norm(r2.path("status").asText(""));
    if ("tool_call".equals(s2)) return fallback("超过工具轮次上限");
    return toResponse(r2);
}
```

## 八、七个关键决策

| 决策 | 理由 |
|---|---|
| 理解放在**运行时**，不放本地 | 否则「AgentArts 只当函数调用器」，平台感没了 |
| 工具由**宿主执行**，不给 runtime 库权限 | 保住「不碰数据」定位；模型只有请求权 |
| 只给三个工具、最多两轮 | 工具与轮次越多越不可控 |
| 判定与条文校验**不经模型** | 可复现是全部数字的地基 |
| `CHAT` 只是**又一个 mode** | 不新增部署，同镜像同运行时 |
| 失败就退回「**手动选天窗**」 | 演示现场不能卡 |
| 响应体带 `status`，不用 HTTP 状态码 | 平台只有一个 `/invocations`，HTTP 由平台包装 |

## 九、与现有能力的关系

```
mode=CHAT              听懂 → 产出 {windowId, taskMode}
taskMode=PRE_REVIEW    → 编排 / 核查 / 仲裁（已上线，云端已验证）
mode=CHECK             → 四节点核查（默认，旧调用不变）
```

**CHAT 不新增判定逻辑**，只把「一句话」变成「一次带参调用」；判定、检索、留痕全部复用现成链路。

## 十一、验收标准

- [ ] 「核查 9 月 23 号那个天窗」→ 直接出结果，`echo` 与前端显示一致
- [ ] 同一天两个窗口时 → 返回 `need_choice`，前端列出候选，点一个能继续
- [ ] 说一个不存在的日期 → 返回 `not_found`，提示最近的天窗
- [ ] 把 runtime 端点改错 → 页面不崩，降级成「手动选择天窗」
- [ ] 模型返回未知 `status` → 后端判 error，不渲染脏数据
- [ ] 日志里没有姓名、电话、完整 payload
- [ ] `#list` / `#gantt` / `#confirm` 三页不受影响

---

## 十二、答辩口径

> 对话入口是**状态机不是聊天**：模型只能申请一次数据，工具由后端执行，最多两轮；它自己没法查库、没法循环。
> 听懂之后落到已有的判定与协商链路——那一段是不经模型的确定性逻辑。
> 所以「AI 会不会乱来」被拆成三层：**意图层只选参数，判定层不碰模型，表达层有引用校验**。

---

## 十三、明确不做

- 不做多轮自由聊天（每轮对话独立，只保留一次工具往返）
- 不做闲聊、不做域外问答
- 不让 runtime 直连数据库或直调后端 HTTP
- 不做流式输出（平台回调限制，且同步更稳）
- 不做「用户自己调工具」这种事——工具执行永远在后端

---

## 附：为什么不能让 runtime 自己调工具

| 方案 | 代价 |
|---|---|
| runtime 直连 MySQL | 要给运行时署数据库凭据，与「不碰数据」的定位冲突 |
| runtime HTTP 调后端 | 后端需公网可达 + 鉴权，暴露面变大 |
| **宿主执行（本方案）** | 后端本来就在内网连库，零新增暴露面 |

一句话：**模型只有「请求权」，执行权留在应用侧。**
